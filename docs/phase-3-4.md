# Phase 3 and Phase 4 implementation record

This document interprets the supplied Phase 3-4 plan against the existing browser-based website. It supersedes conflicting claims in that plan. No native application or mandatory installation is introduced.

## Lifecycle decisions

- Persist `ACTIVE` and `CLOSED` only. Draft is the unsaved creation form. Closing is a confirmation interaction. Successful closure reconciles absences atomically, so a separate partially reconciled persistent state is unnecessary.
- Closed sessions are read-only. Reopening requires a reason and an audit event, preserves recorded attendance and explicit teacher absences, and removes automatic closure absences. Another active session blocks reopening.
- Exporting produces a snapshot rather than an irreversible `EXPORTED` attendance state. Reports can be downloaded repeatedly. The browser cannot prove a requested download reached permanent storage.
- Disputes are review events, separate from attendance outcomes. The first and second presentation times remain available. An unresolved dispute prevents closure. Resolution requires a reason and does not silently modify attendance.
- The F2 shortcut opens a keyboard-accessible manual dialog with search, enrollment context, present/late/excused selection, corrections, and mandatory reasons. Camera capture pauses while the dialog is open.

## Report and recovery changes

Institution, subject, room and timezone are optional session metadata. New imports retain display IDs alongside canonical IDs. Legacy records continue to load with canonical-ID fallback. Excel contains complete attendance and audit worksheets, status shares, widths, a merged heading, filters and percentage formats. CSV includes the full roster and session metadata with BOM, proper quoting, and formula guards. Automatic absences have no fabricated first-check-in timestamp.

Exports read session, attendance and audit rows from one database snapshot. Backups remain encrypted and restore atomically after validation. New backup names end in `.enc.json`; old JSON backups remain supported. Restoration reports actual course, roster-entry and session counts.

## Corrections to the supplied plan

| Original assumption | Implemented interpretation |
| --- | --- |
| Rotating QR eliminates screenshot/proxy attendance | QR is self-asserted data. Timely forwarding and impersonation remain possible. Teacher identity verification is required. |
| AES-GCM guarantees legal compliance after device theft | Encryption is one control. Numeric PIN strength, device compromise, recovery, processing rules and institutional responsibilities remain relevant. |
| autoUpdate with a manual refresh prompt | Keep prompt-based updates and block the update action while a local session is active. |
| Fixed cooldown logs only one event while held for five seconds | Add continuous-target suppression alongside the existing 1.5-second cooldown. A deliberate rescan requires leaving the view and presenting again. |
| Wake lock guarantees full brightness and six-minute operation | Wake lock is optional and can be released. Brightness remains user-controlled. Measure actual supported behavior. |
| 45 students in 3.2 minutes | No real classroom result has been supplied or measured. The defense materials label field results pending. |
| Add to Home Screen required | Use a browser URL. Installation remains optional and outside the required journey. |

## Phase 4 deliverables

- GitHub Actions CI and a manually dispatched GitHub Pages deployment workflow.
- Root-path and repository-subpath build support, secure-context splash, and offline resource checks.
- Teacher and student guides, threat model, corrected panel answers, demo rehearsal protocol.
- Teacher tri-fold PDF, threat-model PDF, editable 12-slide defense deck, and one-slide student onboarding deck generated by the artifact scripts.
- A synthetic 45-student roster, an empty field observation template, field protocol, browser matrix, and a calculation tool that rejects incomplete measurements.

## Completion boundary

Software implementation and automated validation can be completed here. Physical 45-device trials, power-loss tests, actual Safari/Android hardware coverage, institutional privacy review, repository Pages configuration and a successful hosted deployment require external evidence. The presence of a workflow or test protocol does not establish those outcomes.
